# Документ требований: Backend API и База данных

## Введение

Данный документ описывает требования к переходу от MVP версии CrossFit Tracker (работающей на клиенте с localStorage) к полноценному веб-приложению с серверной частью, базой данных, системой аутентификации и развертыванием на хостинге.

Текущее состояние: Vanilla JS/HTML приложение с готовой версткой, все данные хранятся в localStorage браузера, нет аутентификации и серверной логики.

Целевое состояние: Полноценное веб-приложение на базе Next.js 15 с бэкендом (API Routes), базой данных PostgreSQL, системой аутентификации пользователей (Email/Пароль), API для работы с данными, механизмами оффлайн-работы (PWA) и развертыванием с настроенным доменом.

## Глоссарий

- **Система** - веб-приложение CrossFit Tracker в целом
- **Бэкенд** - серверная часть приложения (Next.js API Routes)
- **База_Данных** - PostgreSQL база данных для хранения всех данных приложения
- **Пользователь** - зарегистрированный пользователь приложения
- **Тренировка** - запись о выполненной тренировке (может содержать Skill и/или WOD блоки)
- **Skill_Блок** - силовая часть тренировки с упражнением, подходами, повторениями и весами
- **WOD_Блок** - метаболическая часть тренировки (For Time, AMRAP, EMOM, Tabata)
- **Справочник_Упражнений** - нормализованная таблица упражнений (глобальные + пользовательские)
- **JWT_Токен** - JSON Web Token для аутентификации пользователя
- **Service_Worker** - фоновый скрипт для оффлайн функциональности
- **Транзакция** - атомарная операция базы данных
- **1RM** - одноповторный максимум (расчетный вес для 1 повторения)
- **Тоннаж** - сумма всех весов × повторения за период
- **Стрик** - количество последовательных дней или недель с тренировками
- **Миграция** - процесс переноса данных из localStorage в базу данных

## Требования

### Требование 1: Аутентификация пользователей

**User Story:** Как пользователь, я хочу зарегистрироваться и войти в систему с помощью Email и пароля, чтобы мои данные были защищены и доступны только мне.

#### Критерии приемки

1. КОГДА пользователь открывает приложение без активной сессии, ТО Система ДОЛЖНА отобразить страницу входа/регистрации
2. КОГДА пользователь вводит email и пароль для регистрации, ТО Система ДОЛЖНА создать новый аккаунт со статусом "ожидает подтверждения"
3. КОГДА пользователь регистрируется, ТО Система ДОЛЖНА отправить письмо с кодом подтверждения на указанный email
4. КОГДА пользователь вводит корректные учетные данные для входа, ТО Система ДОЛЖНА создать JWT токен и установить HTTP-only cookie
5. КОГДА пользователь нажимает "Выйти", ТО Система ДОЛЖНА удалить JWT токен из cookie и перенаправить на страницу входа
6. КОГДА пользователь вводит неверный email или пароль, ТО Система ДОЛЖНА вернуть ошибку 401 Unauthorized
7. КОГДА пользователь превышает лимит попыток входа, ТО Система ДОЛЖНА вернуть ошибку 429 Too Many Requests

### Требование 2: Хранение и защита паролей

**User Story:** Как система, я должна безопасно хранить пароли пользователей, чтобы защитить их данные от несанкционированного доступа.

#### Критерии приемки

1. КОГДА пользователь создает пароль, ТО Система ДОЛЖНА хешировать его с использованием bcrypt с cost factor 12
2. КОГДА пользователь входит в систему, ТО Система ДОЛЖНА сравнивать введенный пароль с хешем в базе данных
3. Система ДОЛЖНА валидировать пароль на минимум 8 символов, наличие хотя бы 1 цифры и 1 буквы
4. КОГДА два пользователя создают одинаковый пароль, ТО Система ДОЛЖНА генерировать разные хеши (благодаря salt)

### Требование 3: Генерация и валидация JWT токенов

**User Story:** Как система, я должна генерировать и валидировать JWT токены для аутентификации пользователей.

#### Критерии приемки

1. КОГДА пользователь успешно входит в систему, ТО Система ДОЛЖНА сгенерировать JWT токен со сроком действия 7 дней
2. КОГДА пользователь отправляет запрос к защищенному endpoint, ТО Система ДОЛЖНА извлечь JWT токен из HTTP-only cookie
3. КОГДА JWT токен валиден и не истек, ТО Система ДОЛЖНА извлечь userId и email из payload
4. КОГДА JWT токен невалиден или истек, ТО Система ДОЛЖНА вернуть ошибку 401 Unauthorized
5. КОГДА JWT токен валиден, ТО Система ДОЛЖНА гарантировать, что пользователь с userId существует в базе данных

### Требование 4: Подтверждение email и сброс пароля

**User Story:** Как пользователь, я хочу иметь возможность подтвердить свой email и сбросить пароль, если я его забыл.

#### Критерии приемки

1. КОГДА пользователь регистрируется, ТО Система ДОЛЖНА сгенерировать одноразовый токен верификации
2. КОГДА пользователь переходит по ссылке с токеном верификации, ТО Система ДОЛЖНА установить флаг verified = true
3. КОГДА пользователь запрашивает сброс пароля, ТО Система ДОЛЖНА сгенерировать одноразовый токен сброса со сроком действия 1 час
4. КОГДА пользователь использует токен сброса пароля, ТО Система ДОЛЖНА удалить токен из базы данных
5. КОГДА токен верификации или сброса истек, ТО Система ДОЛЖНА вернуть ошибку 400 Bad Request

### Требование 5: Структура базы данных

**User Story:** Как разработчик, я хочу иметь нормализованную структуру базы данных для быстрых запросов и точной статистики.

#### Критерии приемки

1. Все первичные ключи во всех таблицах ДОЛЖНЫ иметь тип UUID v4
2. Таблица users ДОЛЖНА содержать поля: id, email, password_hash, first_name, last_name, avatar, verified, created_at, updated_at
3. Таблица exercises_dict ДОЛЖНА содержать поля: id, name, is_global, user_id, created_at
4. Таблица workouts ДОЛЖНА содержать поля: id, user_id, date (YYYY-MM-DD), comment, created_at, updated_at
5. Таблица skill_blocks ДОЛЖНА содержать поля: id, workout_id, exercise_dict_id, created_at
6. Таблица skill_sets ДОЛЖНА содержать поля: id, skill_block_id, set_number, reps, weight (Decimal 6,2)
7. Таблица wod_blocks ДОЛЖНА содержать поля: id, workout_id, wod_type, level, time_cap_seconds, is_ladder, result_type, result_display, result_seconds, result_total_reps
8. Таблица wod_exercises ДОЛЖНА содержать поля: id, wod_block_id, exercise_dict_id, reps, weight, order_index
9. КОГДА пользователь удаляется, ТО Система ДОЛЖНА каскадно удалить все связанные тренировки и данные

### Требование 6: Справочник упражнений

**User Story:** Как пользователь, я хочу, чтобы статистика по упражнениям считалась корректно, даже если я ввел название с разным регистром.

#### Критерии приемки

1. База_Данных ДОЛЖНА содержать предустановленный глобальный справочник из 15 популярных кроссфит-упражнений
2. КОГДА пользователь вводит название упражнения, ТО Система ДОЛЖНА искать его в справочнике без учета регистра
3. КОГДА упражнение найдено в глобальном справочнике, ТО Система ДОЛЖНА использовать его ID
4. КОГДА упражнение не найдено, ТО Система ДОЛЖНА создать новое пользовательское упражнение с is_global = false
5. КОГДА пользователь создает упражнение с названием, уже существующим в его личном справочнике, ТО Система ДОЛЖНА использовать существующий ID

### Требование 7: Создание тренировки с транзакцией

**User Story:** Как пользователь, я хочу создавать тренировки с несколькими блоками, и чтобы все данные сохранялись атомарно.

#### Критерии приемки

1. КОГДА пользователь создает тренировку, ТО Система ДОЛЖНА начать транзакцию базы данных
2. КОГДА любой шаг создания тренировки завершается ошибкой, ТО Система ДОЛЖНА откатить всю транзакцию
3. КОГДА все шаги создания тренировки успешны, ТО Система ДОЛЖНА зафиксировать транзакцию
4. КОГДА тренировка создается, ТО Система ДОЛЖНА автоматически резолвить названия упражнений в exercise_dict_id
5. КОГДА тренировка создается, ТО Система ДОЛЖНА установить userId равным ID текущего пользователя
6. КОГДА тренировка создается, ТО Система ДОЛЖНА установить createdAt на текущее время

### Требование 8: Валидация данных тренировки

**User Story:** Как система, я должна валидировать данные тренировки перед сохранением в базу данных.

#### Критерии приемки

1. КОГДА дата тренировки в будущем, ТО Система ДОЛЖНА вернуть ошибку 400 Bad Request
2. КОГДА вес в skill_set меньше 0.5 кг, ТО Система ДОЛЖНА вернуть ошибку 400 Bad Request
3. КОГДА вес в skill_set больше 9999.99 кг, ТО Система ДОЛЖНА вернуть ошибку 400 Bad Request
4. КОГДА количество повторений меньше 1, ТО Система ДОЛЖНА вернуть ошибку 400 Bad Request
5. КОГДА комментарий длиннее 500 символов, ТО Система ДОЛЖНА вернуть ошибку 400 Bad Request
6. КОГДА тренировка не содержит ни одного блока, ТО Система ДОЛЖНА вернуть ошибку 400 Bad Request
7. КОГДА wod_type = FOR_TIME и result_seconds = null, ТО Система ДОЛЖНА вернуть ошибку 400 Bad Request
8. КОГДА wod_type = AMRAP и result_total_reps = null, ТО Система ДОЛЖНА вернуть ошибку 400 Bad Request

### Требование 9: Получение списка тренировок

**User Story:** Как пользователь, я хочу просматривать историю своих тренировок с возможностью фильтрации и пагинации.

#### Критерии приемки

1. КОГДА пользователь запрашивает список тренировок, ТО Система ДОЛЖНА вернуть только тренировки этого пользователя
2. КОГДА пользователь указывает параметр page, ТО Система ДОЛЖНА вернуть соответствующую страницу результатов
3. КОГДА пользователь указывает параметр limit, ТО Система ДОЛЖНА вернуть не более указанного количества тренировок
4. КОГДА пользователь указывает startDate и endDate, ТО Система ДОЛЖНА вернуть только тренировки в этом диапазоне
5. КОГДА пользователь указывает exerciseId, ТО Система ДОЛЖНА вернуть только тренировки, содержащие это упражнение
6. КОГДА пользователь запрашивает список тренировок, ТО Система ДОЛЖНА отсортировать их по дате в порядке убывания

### Требование 10: Получение и изменение одной тренировки

**User Story:** Как пользователь, я хочу просматривать детали тренировки и иметь возможность ее редактировать или удалять.

#### Критерии приемки

1. КОГДА пользователь запрашивает тренировку по ID, ТО Система ДОЛЖНА вернуть полный объект со всеми вложенными блоками
2. КОГДА пользователь запрашивает чужую тренировку, ТО Система ДОЛЖНА вернуть ошибку 403 Forbidden
3. КОГДА пользователь запрашивает несуществующую тренировку, ТО Система ДОЛЖНА вернуть ошибку 404 Not Found
4. КОГДА пользователь обновляет тренировку, ТО Система ДОЛЖНА проверить, что userId совпадает
5. КОГДА пользователь удаляет тренировку, ТО Система ДОЛЖНА каскадно удалить все связанные блоки и подходы
6. КОГДА пользователь повторно удаляет уже удаленную тренировку, ТО Система ДОЛЖНА вернуть тот же результат (идемпотентность)

### Требование 11: Расчет 1RM (одноповторного максимума)

**User Story:** Как пользователь, я хочу видеть расчетный одноповторный максимум для каждого упражнения.

#### Критерии приемки

1. КОГДА количество повторений равно 1, ТО Система ДОЛЖНА вернуть вес как 1RM
2. КОГДА количество повторений больше 1, ТО Система ДОЛЖНА рассчитать 1RM по формуле Эпли: 1RM = weight × (1 + reps / 30)
3. КОГДА 1RM рассчитан, ТО Система ДОЛЖНА округлить результат до 0.5 кг
4. КОГДА 1RM рассчитан, ТО результат ДОЛЖЕН быть больше или равен рабочему весу

### Требование 12: Расчет тоннажа

**User Story:** Как пользователь, я хочу видеть суммарный тоннаж за период, чтобы отслеживать объем тренировок.

#### Критерии приемки

1. КОГДА пользователь запрашивает тоннаж за период, ТО Система ДОЛЖНА суммировать (вес × повторения) для всех skill_sets
2. КОГДА в периоде нет тренировок, ТО Система ДОЛЖНА вернуть тоннаж = 0
3. КОГДА пользователь добавляет тренировку с skill блоками, ТО тоннаж за этот день ДОЛЖЕН увеличиться
4. КОГДА тренировка содержит только WOD блоки без skill блоков, ТО она НЕ ДОЛЖНА влиять на тоннаж

### Требование 13: Расчет стрика

**User Story:** Как пользователь, я хочу видеть свой текущий стрик тренировок, чтобы поддерживать мотивацию.

#### Критерии приемки

1. КОГДА у пользователя нет тренировок, ТО Система ДОЛЖНА вернуть стрик = 0 дней и 0 недель
2. КОГДА последняя тренировка была более 1 дня назад, ТО Система ДОЛЖНА вернуть стрик = 0 дней
3. КОГДА пользователь тренировался N дней подряд, ТО Система ДОЛЖНА вернуть стрик = N дней
4. КОГДА пользователь тренировался хотя бы 1 раз в каждой из последних N недель, ТО Система ДОЛЖНА вернуть стрик = N недель
5. КОГДА пользователь пропустил день, ТО стрик по дням ДОЛЖЕН сброситься до 0

### Требование 14: Статистика по упражнению

**User Story:** Как пользователь, я хочу видеть свои личные рекорды и историю прогресса по каждому упражнению.

#### Критерии приемки

1. КОГДА пользователь запрашивает статистику по упражнению, ТО Система ДОЛЖНА вернуть максимальный вес
2. КОГДА пользователь запрашивает статистику по упражнению, ТО Система ДОЛЖНА вернуть максимальное количество повторений
3. КОГДА пользователь запрашивает статистику по упражнению, ТО Система ДОЛЖНА вернуть лучший расчетный 1RM
4. КОГДА пользователь запрашивает статистику по упражнению, ТО Система ДОЛЖНА вернуть историю всех подходов с датами
5. КОГДА пользователь указывает период, ТО Система ДОЛЖНА вернуть статистику только за этот период

### Требование 15: Dashboard метрики

**User Story:** Как пользователь, я хочу видеть сводную статистику на главной странице.

#### Критерии приемки

1. КОГДА пользователь открывает Dashboard, ТО Система ДОЛЖНА вернуть количество тренировок за текущий месяц
2. КОГДА пользователь открывает Dashboard, ТО Система ДОЛЖНА вернуть тоннаж за текущий месяц
3. КОГДА пользователь открывает Dashboard, ТО Система ДОЛЖНА вернуть текущий стрик (дни и недели)
4. КОГДА пользователь открывает Dashboard, ТО Система ДОЛЖНА вернуть список последних 5-10 тренировок

### Требование 16: Миграция данных из localStorage

**User Story:** Как пользователь, я хочу перенести свои локальные данные в облако при первом входе.

#### Критерии приемки

1. КОГДА пользователь отправляет данные для миграции, ТО Система ДОЛЖНА обработать каждую тренировку отдельно
2. КОГДА тренировка валидна, ТО Система ДОЛЖНА создать ее в базе данных
3. КОГДА тренировка невалидна, ТО Система ДОЛЖНА пропустить ее и добавить ошибку в отчет
4. КОГДА миграция завершена, ТО Система ДОЛЖНА вернуть количество импортированных и неудачных тренировок
5. КОГДА название упражнения из localStorage не найдено в справочнике, ТО Система ДОЛЖНА создать новое пользовательское упражнение
6. КОГДА миграция завершена, ТО Система ДОЛЖНА сохранить оригинальные даты тренировок

### Требование 17: Rate Limiting

**User Story:** Как система, я должна защищать API от злоупотреблений и атак.

#### Критерии приемки

1. КОГДА пользователь превышает 5 попыток входа за 15 минут, ТО Система ДОЛЖНА вернуть ошибку 429 Too Many Requests
2. КОГДА пользователь превышает 100 запросов к API за минуту, ТО Система ДОЛЖНА вернуть ошибку 429 Too Many Requests
3. КОГДА пользователь превышает 1 запрос миграции за 5 минут, ТО Система ДОЛЖНА вернуть ошибку 429 Too Many Requests
4. КОГДА пользователь получает ошибку 429, ТО Система ДОЛЖНА вернуть заголовок Retry-After с временем ожидания

### Требование 18: PWA функциональность

**User Story:** Как пользователь, я хочу, чтобы приложение работало оффлайн и устанавливалось на домашний экран.

#### Критерии приемки

1. Система ДОЛЖНА предоставлять manifest.json с корректными метаданными приложения
2. Система ДОЛЖНА регистрировать Service Worker для кэширования ресурсов
3. КОГДА пользователь оффлайн, ТО статические файлы ДОЛЖНЫ загружаться из кэша
4. КОГДА пользователь оффлайн, ТО справочник упражнений ДОЛЖЕН быть доступен из кэша
5. Manifest ДОЛЖЕН содержать display: standalone для полноэкранного режима
6. Manifest ДОЛЖЕН содержать theme_color: #DC2626 и background_color: #1A1A1A

### Требование 19: Оффлайн создание тренировок

**User Story:** Как пользователь, я хочу создавать тренировки без интернета, и чтобы они автоматически синхронизировались при подключении.

#### Критерии приемки

1. КОГДА пользователь создает тренировку оффлайн, ТО Система ДОЛЖНА сохранить ее в IndexedDB со статусом "ожидает синхронизации"
2. КОГДА интернет появляется, ТО Service_Worker ДОЛЖЕН автоматически отправить все ожидающие тренировки на сервер
3. КОГДА синхронизация успешна, ТО Система ДОЛЖНА удалить тренировку из очереди IndexedDB
4. КОГДА синхронизация неуспешна, ТО Система ДОЛЖНА оставить тренировку в очереди для повторной попытки
5. КОГДА синхронизация завершена, ТО Система ДОЛЖНА уведомить пользователя о количестве синхронизированных тренировок

### Требование 21: Безопасность API

**User Story:** Как система, я должна защищать данные пользователей от несанкционированного доступа.

#### Критерии приемки

1. Все API endpoints (кроме auth) ДОЛЖНЫ проверять наличие валидного JWT токена
2. КОГДА JWT токен отсутствует или невалиден, ТО Система ДОЛЖНА вернуть ошибку 401 Unauthorized
3. КОГДА пользователь пытается получить доступ к чужим данным, ТО Система ДОЛЖНА вернуть ошибку 403 Forbidden

5. Система ДОЛЖНА устанавливать HTTP-only флаг для JWT cookie для защиты от XSS
6. Система ДОЛЖНА устанавливать SameSite=Lax для JWT cookie для защиты от CSRF
7. Система ДОЛЖНА использовать HTTPS в production для защиты данных при передаче

## Корректные свойства (Correctness Properties)

*Свойство — это характеристика или поведение, которое должно выполняться для всех валидных выполнений системы. По сути, это формальное утверждение о том, что должна делать система. Свойства служат мостом между человекочитаемыми спецификациями и машинно-проверяемыми гарантиями корректности.*

### Свойство 1: Атомарность транзакций создания тренировки

*Для любой* попытки создания тренировки, если транзакция начата и любой шаг завершается ошибкой, то все изменения должны быть откачены; если все шаги успешны, то все изменения должны быть зафиксированы.

**Валидирует: Требования 7.2, 7.3**

### Свойство 2: Изоляция данных пользователей

*Для любых* двух пользователей user1 и user2, если тренировка принадлежит user1 и user1 ≠ user2, то user2 не может получить доступ к этой тренировке.

**Валидирует: Требования 9.1, 10.2, 21.3**

### Свойство 3: Монотонность 1RM

*Для любого* веса и количества повторений, если оба значения положительны, то расчетный 1RM должен быть больше или равен рабочему весу.

**Валидирует: Требование 11.4**

### Свойство 4: Консистентность резолва упражнений

*Для любого* названия упражнения и пользователя, повторный резолв одного и того же названия упражнения для одного пользователя всегда должен возвращать один и тот же ID.

**Валидирует: Требования 6.3, 6.4, 6.5**

### Свойство 5: Идемпотентность удаления тренировки

*Для любой* тренировки и пользователя, повторное удаление одной и той же тренировки должно приводить к тому же результату без ошибок.

**Валидирует: Требование 10.6**

### Свойство 6: Валидность JWT токенов

*Для любого* JWT токена, если токен валиден и не истек, то должен существовать пользователь с userId и email из payload токена.

**Валидирует: Требования 3.3, 3.4, 3.5**

### Свойство 7: Монотонность тоннажа

*Для любого* пользователя и даты, если добавляется тренировка с skill блоками, то тоннаж за этот день должен увеличиться или остаться прежним.

**Валидирует: Требование 12.3**

### Свойство 8: Корректность стрика при отсутствии недавних тренировок

*Для любого* пользователя, если последняя тренировка была более 1 дня назад, то стрик по дням должен быть равен 0.

**Валидирует: Требования 13.2, 13.5**

### Свойство 9: Уникальность email пользователей

*Для любых* двух пользователей, если их ID различны, то их email адреса также должны различаться.

**Валидирует: Требование 5.2**

### Свойство 10: Безопасность хеширования паролей

*Для любого* пароля, хеш этого пароля никогда не должен совпадать с оригинальным паролем.

**Валидирует: Требование 2.1**

### Свойство 11: Уникальность хешей паролей с солью

*Для любого* пароля, если два пользователя создают одинаковый пароль, то их хеши должны различаться благодаря использованию соли.

**Валидирует: Требование 2.4**

### Свойство 12: Консистентность оффлайн синхронизации

*Для любой* тренировки в очереди ожидания, если синхронизация успешна, то тренировка должна быть удалена из локальной очереди и присутствовать на сервере.

**Валидирует: Требования 19.2, 19.3**

### Свойство 13: Валидность дат тренировок

*Для любой* тренировки, дата тренировки не должна быть в будущем.

**Валидирует: Требование 8.1**

### Свойство 14: Диапазон весов

*Для любого* подхода в skill блоке, вес должен быть в диапазоне от 0.5 до 9999.99 кг включительно.

**Валидирует: Требования 8.2, 8.3**

### Свойство 15: Последовательность номеров подходов

*Для любого* skill блока, если подходы отсортированы по set_number, то номера подходов должны быть последовательными и начинаться с 1.

**Валидирует: Требование 7.4**

### Свойство 16: Соответствие результатов WOD типу комплекса

*Для любого* WOD блока, если тип комплекса FOR_TIME, то result_seconds не должен быть null; если тип AMRAP, то result_total_reps не должен быть null.

**Валидирует: Требования 8.7, 8.8**

### Свойство 17: Округление 1RM до 0.5 кг

*Для любого* расчета 1RM, результат должен быть округлен до ближайшего значения, кратного 0.5 кг.

**Валидирует: Требование 11.3**

### Свойство 18: Тоннаж только для Skill блоков

*Для любой* тренировки, содержащей только WOD блоки без skill блоков, тоннаж за этот день не должен измениться.

**Валидирует: Требование 12.4**

### Свойство 19: Стрик по неделям

*Для любого* пользователя, если пользователь тренировался хотя бы 1 раз в каждой из последних N недель подряд, то стрик по неделям должен быть равен N.

**Валидирует: Требование 13.4**

### Свойство 20: Каскадное удаление данных пользователя

*Для любого* пользователя, если пользователь удаляется, то все связанные тренировки, skill блоки, skill подходы, WOD блоки и WOD упражнения должны быть удалены.

**Валидирует: Требования 5.9, 23.4**

### Свойство 21: Сохранение оригинальных дат при миграции

*Для любой* тренировки из localStorage, после успешной миграции дата тренировки в базе данных должна совпадать с оригинальной датой.

**Валидирует: Требование 16.6**

### Свойство 22: Автоматическое создание пользовательских упражнений

*Для любого* названия упражнения, не найденного в справочнике, система должна создать новое пользовательское упражнение с is_global = false и вернуть его ID.

**Валидирует: Требования 6.4, 16.5**

### Свойство 23: Срок действия токенов верификации

*Для любого* токена верификации или сброса пароля, если прошло более 1 часа с момента создания, то токен должен быть признан истекшим.

**Валидирует: Требование 4.5**

### Свойство 24: Одноразовость токенов сброса пароля

*Для любого* токена сброса пароля, после успешного использования токен должен быть удален из базы данных и не может быть использован повторно.

**Валидирует: Требование 4.4**

### Свойство 25: Rate Limiting для auth endpoints

*Для любого* IP адреса или пользователя, если количество запросов к auth endpoints превышает 5 за 15 минут, то последующие запросы должны возвращать ошибку 429.

**Валидирует: Требования 1.7, 17.1**
