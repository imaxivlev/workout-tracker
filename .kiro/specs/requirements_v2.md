# Документ требований: Backend, База данных и Деплой (v2)

## Введение

Данный документ описывает требования к переходу от MVP версии CrossFit Tracker (работающей на клиенте с localStorage) к полноценному веб-приложению с серверной частью, базой данных, системой аутентификации и развертыванием на хостинге.

Текущее состояние: Vanilla JS/HTML приложение с готовой версткой, все данные хранятся в localStorage браузера, нет аутентификации и серверной логики.

Целевое состояние: Полноценное веб-приложение с бэкендом (Next.js API Routes или аналогичный Node.js фреймворк), базой данных PostgreSQL, системой аутентификации пользователей (Email/Пароль), API для работы с данными, механизмами оффлайн-работы (PWA) и развертыванием с настроенным доменом.

## Глоссарий

- **Система** - веб-приложение CrossFit Tracker в целом
- **Бэкенд** - серверная часть приложения (API)
- **База Данных (БД)** - PostgreSQL база данных для хранения всех данных приложения
- **Пользователь** - зарегистрированный пользователь приложения
- **Тренировка** - запись о выполненной тренировке (может содержать Skill и/или WOD блоки)
- **Skill Блок** - силовая часть тренировки с упражнением, подходами, повторениями и весами (все веса строго в кг)
- **WOD Блок** - метаболическая часть тренировки (For Time, AMRAP, EMOM, Tabata)
- **Уровень WOD** - стандарт выполнения комплекса: Rx (как предписано) или Scaled (масштабировано)
- **Личный Рекорд (PR)** - лучший результат пользователя по конкретному упражнению или максимальный расчетный вес на 1 повторение (1RM)
- **Миграция** - процесс переноса данных из localStorage в базу данных

## Требования

### Требование 1: Аутентификация и управление пользователями

**User Story:** Как пользователь, я хочу зарегистрироваться и войти в систему с помощью Email, чтобы мои данные были защищены и доступны только мне.

#### Критерии приемки
1. КОГДА пользователь открывает приложение без активной сессии, ТО Система ДОЛЖНА отобразить страницу входа/регистрации.
2. КОГДА пользователь вводит email и пароль для регистрации, ТО Система ДОЛЖНА создать новый аккаунт со статусом "ожидает подтверждения" и отправить письмо с кодом/ссылкой подтверждения.
3. Система ДОЛЖНА поддерживать **ТОЛЬКО** регистрацию по Email/Паролю (без OAuth-провайдеров типа Google/Apple в соответствии с требованиями и локальным законодательством).
4. КОГДА пользователь вводит корректные учетные данные, ТО Система ДОЛЖНА создать защищенную сессию (JWT в HTTP-only cookie) и перенаправить на главную.
5. КОГДА пользователь нажимает "Выйти", ТО Система ДОЛЖНА завершить сессию (удалить cookie) и перенаправить на страницу входа.
6. Система ДОЛЖНА хранить пароли в зашифрованном виде (bcrypt/Argon2).

### Требование 2: Профиль пользователя и приватность

**User Story:** Как пользователь, я хочу управлять своим профилем и иметь возможность удалить свои данные.

#### Критерии приемки
1. Система ДОЛЖНА хранить: email, имя, фамилию, дату регистрации, аватар.
2. КОГДА пользователь изменяет данные, ТО Система ДОЛЖНА обновить их в БД.
3. Система ДОЛЖНА валидировать формат email при изменении и запрашивать подтверждение нового ящика.
4. **Удаление аккаунта:** Система ДОЛЖНА предоставлять функцию полного удаления профиля (соответствие законам о ПД). При удалении все связанные тренировки и данные пользователя должны быть безвозвратно удалены (либо анонимизированы).

### Требование 3: Почтовая инфраструктура (Уведомления)

**User Story:** Как Система, я должна уметь надежно доставлять транзакционные письма пользователям (регистрация, сброс пароля).

#### Критерии приемки
1. Бэкенд ДОЛЖЕН быть интегрирован с почтовым SMTP-провайдером (например, Яндекс.Почта для домена, Mail.ru Cloud Solutions или специализированные сервисы).
2. Система ДОЛЖНА содержать HTML-шаблоны писем: "Подтверждение Email" и "Сброс пароля".
3. КОГДА сервис отправки писем недоступен, ТО Бэкенд ДОЛЖЕН логировать ошибку, а Система ДОЛЖНА уведомить пользователя о задержке отправки.
4. Ссылки в письмах для сброса пароля ДОЛЖНЫ иметь ограниченный срок действия (например, 1 час) и являться одноразовыми.

### Требование 4: Справочник упражнений (Нормализация)

**User Story:** Как пользователь, я хочу, чтобы статистика по упражнениям (например, "Snatch" или "Рывок") считалась корректно, даже если я ввел название с маленькой буквы или опечаткой.

#### Критерии приемки
1. База Данных ДОЛЖНА содержать предустановленный глобальный справочник популярных кроссфит-упражнений.
2. КОГДА пользователь вводит название упражнения в UI, ТО Система ДОЛЖНА предлагать автодополнение из справочника.
3. КОГДА пользователь вводит новое уникальное упражнение, ТО оно ДОЛЖНО сохраняться в БД привязанным к профилю пользователя (личный словарь).
4. Вся статистика и PR ДОЛЖНЫ агрегироваться по ID упражнения из справочника, а не по сырому тексту.

### Требование 5: Структура базы данных и типизация

**User Story:** Как разработчик, я хочу иметь нормализованную структуру БД для быстрых запросов, замера времени и точной статистики.

#### Критерии приемки
1. Все первичные ключи (ID) во всех таблицах ДОЛЖНЫ иметь тип **UUID (v4)** для исключения конфликтов при синхронизации/миграции.
2. Таблица `users`: `id`, `email`, `password_hash`, `first_name`, `last_name`, `created_at`.
3. Таблица `exercises_dict`: `id`, `name`, `is_global`, `user_id` (null для глобальных).
4. Таблица `workouts`: `id`, `user_id`, `date` (формат YYYY-MM-DD для исключения сдвигов часовых поясов), `comment`, `created_at`.
5. Таблица `skill_blocks`: `id`, `workout_id`, `exercise_dict_id`.
6. Таблица `skill_sets` (нормализация подходов): `id`, `skill_block_id`, `set_number`, `reps`, `weight` (numeric). Никаких массивов в колонках.
7. Таблица `wod_blocks`: `id`, `workout_id`, `wod_type` (Enum), `level` (Enum: Rx, Scaled), `time_cap_seconds` (int), `is_ladder` (bool), `result_type` (Enum: time, reps, weight).
8. **Хранение результатов WOD**:
   - `result_display` (string) — то, что ввел пользователь ("15:30", "5+12").
   - `result_seconds` (int) — для типов "time" (чтобы можно было делать ORDER BY ASC для поиска рекордов).
   - `result_total_reps` (int) — для "AMRAP" (ORDER BY DESC).
9. Таблица `wod_exercises`: `id`, `wod_block_id`, `exercise_dict_id`, `reps`, `weight`.

### Требование 6: API для работы с тренировками

**User Story:** Как клиентское приложение, я хочу получать и отправлять данные структурированно и безопасно.

#### Критерии приемки
1. Бэкенд ДОЛЖЕН реализовывать RESTful или GraphQL API.
2. КОГДА клиент запрашивает сохранение тренировки, ТО Бэкенд сохраняет ее вместе со всеми вложенными `skill_blocks`, `skill_sets` и `wod_blocks` в рамках одной БД транзакции.
3. КОГДА запрос содержит некорректные данные, ТО Бэкенд возвращает 400 Bad Request.
4. Все эндпоинты (кроме аутентификации) ДОЛЖНЫ проверять JWT токен. Попытка доступа к чужим `user_id` ДОЛЖНА возвращать 403 Forbidden.

### Требование 7: Фильтрация, Поиск и Пагинация

#### Критерии приемки
1. КОГДА пользователь прокручивает историю, ТО Бэкенд ДОЛЖЕН отдавать данные порциями (пагинация/infinite scroll) для экономии трафика приложения (например, по 20 тренировок).
2. КОГДА пользователь выбирает упражнение в фильтре, ТО фильтрация происходит по `exercise_dict_id`.
3. Бэкенд ДОЛЖЕН возвращать данные отсортированными по локальной `date` тренировки.

### Требование 8: Расчет статистики и 1RM (Одноповторный максимум)

**User Story:** Как пользователь, я хочу видеть свои рекорды и расчетный максимум, чтобы планировать веса для новых тренировок.

#### Критерии приемки
1. Бэкенд ДОЛЖЕН определять личные абсолютные рекорды (PR) по каждому упражнению.
2. Для Skill блоков Бэкенд ДОЛЖЕН автоматически рассчитывать 1RM (одноповторный максимум) по стандартной формуле (например, Эпли или Бржицки), если выполнено больше 1 повторения.
3. Бэкенд ДОЛЖЕН предоставлять API для получения истории 1RM для построения графика прогресса в Chart.js.
4. **Визуализация:**
   - Использовать библиотеку Chart.js для графиков
   - График прогресса по упражнению (линейный график)
   - График тоннажа за период (столбчатый график)
   - Темная тема графиков (соответствие дизайну)
5. Веса ВСЕГДА считаются и возвращаются только в килограммах (kg), функционал смены метрической системы исключается.

### Требование 9: Миграция данных из localStorage

**User Story:** Как текущий пользователь, я хочу перенести локальные данные в облако.

#### Критерии приемки
1. КОГДА пользователь входит в аккаунт, веб-клиент ДОЛЖЕН проверить наличие ключей в `localStorage`.
2. Если тренировки есть, клиент предлагает "Синхронизировать данные".
3. Данные из localStorage отправляются POST-запросом на специальный эндпоинт миграции.
4. Так как старые данные содержат строковые названия упражнений, Бэкенд ДОЛЖЕН автоматически подобрать подходящий `exercise_dict_id` (или создать новые пользовательские упражнения) при сохранении.
5. После успешного ответа 200 OK, клиент очищает localStorage.

### Требование 10: Оффлайн режим (PWA)

**User Story:** Как пользователь, тренирующийся в подвале, я хочу чтобы приложение работало и сохраняло тренировки без подключения к интернету.

#### Критерии приемки
1. Платформа ДОЛЖНА быть настроена как PWA (Service Workers, Manifest).
2. **Manifest.json ДОЛЖЕН содержать:**
   - `name`: "CrossFit Tracker"
   - `short_name`: "CF Tracker"
   - `start_url`: "/"
   - `display`: "standalone" (полноэкранный режим без браузерного UI)
   - `theme_color`: "#DC2626" (красный акцент)
   - `background_color`: "#1A1A1A" (темный фон)
   - Иконки: 192x192, 512x512 (PNG)
3. Статические файлы (HTML, CSS, JS) и кэш справочника упражнений ДОЛЖНЫ быть закешированы на устройстве.
4. КОГДА сети нет, новая тренировка сохраняется локально в IndexedDB со статусом "ожидает синхронизации".
5. КОГДА интернет появляется, клиент ДОЛЖЕН фоново отправить все ожидающие тренировки на сервер по API.
6. **Установка PWA:**
   - На iOS: Safari → "Поделиться" → "На экран Домой"
   - На Android: Chrome → "Установить приложение"
   - Приложение ДОЛЖНО открываться в standalone режиме (без адресной строки браузера)

### Требование 11: Производительность и Безопасность

#### Критерии приемки
1. Использование параметризованных запросов SQL (ORMs/Query Builders) для защиты от инъекций.
2. Rate Limiting для эндпоинтов логина/регистрации (защита от брутфорса) и сброса пароля.
3. Использование индексов БД на полях: `user_id`, `date`, `exercise_dict_id`.
4. HTTPS обязательно.

### Требование 12: Деплой (Vercel/Аналоги) и Мониторинг

#### Критерии приемки
1. Автоматический деплой из main-ветки.
2. Секреты (строка подключения к БД, JWT_SECRET, параметры SMTP сервера) хранятся в переменных окружения.
3. Логирование HTTP 500 ошибок (стек-трейсы) в консоли или внешней системе мониторинга (Sentry/Vercel Logs).
4. Настроенный Custom домен с SSL-сертификатом.
5. Автоматические ежедневные бэкапы базы данных (обеспечивается хостером Postgres, например Supabase/Neon/Render).

### Требование 13: UI/UX и Адаптивность

**User Story:** Как пользователь, я хочу удобно пользоваться приложением на любом устройстве.

#### Критерии приемки
1. **Дизайн:**
   - Темная тема (фон #1A1A1A, акцент #DC2626 красный)
   - Агрессивный CrossFit стиль
   - Крупные шрифты для удобства в зале
2. **Адаптивность:**
   - Десктоп (>768px): Верхняя навигация с логотипом
   - Мобильные (<769px): Нижнее меню (bottom navigation) с 5 иконками
   - Все формы и модальные окна адаптированы под мобильные
3. **Навигация:**
   - **Десктоп (верхнее меню):**
     - Логотип → Главная
     - История (отдельная ссылка)
     - Статистика
     - Кнопка "Новая тренировка"
     - Аватар → Профиль
   - **Мобильные (нижнее меню, 5 иконок):**
     - 🏠 Главная (Dashboard с последними тренировками и метриками)
     - 🕐 История (список всех тренировок с фильтрами)
     - ➕ Создать (форма создания тренировки)
     - 📊 Статистика (графики, PR, прогресс)
     - 👤 Профиль (настройки пользователя)
4. **Формы создания тренировки:**
   - Конструктор блоков (Skill + WOD)
   - Автодополнение упражнений из справочника
   - На мобильных: горизонтальная прокрутка полей WOD упражнений
   - Поддержка "лесенки" (ladder) с несколькими раундами
5. **Календарь/Фильтр периода:**
   - На десктопе: 3 месяца
   - На мобильных: 1 месяц, центрированное модальное окно с затемнением фона
   - Presets: "Вчера", "Неделя", "Месяц", "Год"

### Требование 14: Единицы измерения

**User Story:** Как пользователь из России, я хочу работать только с метрической системой.

#### Критерии приемки
1. Все веса ДОЛЖНЫ храниться и отображаться ТОЛЬКО в килограммах (kg).
2. Функционал переключения на фунты (lbs) НЕ реализуется (соответствие локальному рынку).
3. В UI везде указывается "кг" или "kg" явно.
4. Валидация: вес должен быть положительным числом с точностью до 0.5 кг (например, 62.5 кг).

### Требование 15: Dashboard и Мотивационные метрики

**User Story:** Как пользователь, я хочу видеть свой прогресс и мотивирующие показатели на главной странице.

#### Критерии приемки
1. **Dashboard ДОЛЖЕН отображать:**
   - Количество тренировок за текущий месяц
   - Тоннаж за месяц (сумма всех весов × повторения из Skill блоков)
   - Текущий стрик (дней подряд / недель подряд)
   - Ленту последних 5-10 тренировок
2. **Расчет стрика:**
   - Стрик считается по дням: если пользователь тренировался N дней подряд
   - Стрик прерывается, если пропущен 1 день
   - Альтернативный стрик по неделям: если в каждой неделе была хотя бы 1 тренировка
3. **Тоннаж:**
   - Считается только для Skill блоков
   - Формула: Σ(вес × повторения) для всех подходов всех упражнений
   - Отображается в тоннах (если > 1000 кг) или кг
4. **Лента тренировок:**
   - Карточки с датой, типом (Skill/WOD/оба), кратким описанием
   - Клик по карточке → детальный просмотр тренировки
