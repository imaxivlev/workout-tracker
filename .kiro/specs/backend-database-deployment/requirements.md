# Документ требований: Backend, База данных и Деплой

## Введение

Данный документ описывает требования к переходу от MVP версии CrossFit Tracker (работающей на клиенте с localStorage) к полноценному веб-приложению с серверной частью, базой данных, системой аутентификации и развертыванием на хостинге.

Текущее состояние: Next.js приложение с готовой версткой в `/public/workout-tracker/`, все данные хранятся в localStorage браузера, нет аутентификации и серверной логики.

Целевое состояние: Полноценное веб-приложение с бэкендом, базой данных PostgreSQL, системой аутентификации пользователей, API для работы с данными и развертыванием на Vercel с настроенным доменом.

## Глоссарий

- **Система** - веб-приложение CrossFit Tracker в целом
- **Бэкенд** - серверная часть приложения (Next.js API Routes)
- **База_Данных** - PostgreSQL база данных для хранения всех данных приложения
- **Пользователь** - зарегистрированный пользователь приложения
- **Тренировка** - запись о выполненной тренировке (может содержать Skill и/или WOD блоки)
- **Skill_Блок** - силовая часть тренировки с упражнением, подходами, повторениями и весами
- **WOD_Блок** - метаболическая часть тренировки (For Time, AMRAP, EMOM, Tabata)
- **Личный_Рекорд** (PR) - лучший результат пользователя по конкретному упражнению
- **Статистика** - агрегированные данные о тренировках пользователя
- **Аутентификация** - процесс проверки личности пользователя
- **API** - программный интерфейс для взаимодействия клиента с сервером
- **Миграция** - процесс переноса данных из localStorage в базу данных

## Требования

### Требование 1: Аутентификация и управление пользователями

**User Story:** Как пользователь, я хочу зарегистрироваться и войти в систему, чтобы мои данные были защищены и доступны только мне.

#### Критерии приемки

1. КОГДА пользователь открывает приложение без активной сессии, ТО Система ДОЛЖНА отобразить страницу входа
2. КОГДА пользователь вводит email и пароль для регистрации, ТО Система ДОЛЖНА создать новый аккаунт и отправить письмо для подтверждения email
3. КОГДА пользователь вводит корректные учетные данные для входа, ТО Система ДОЛЖНА создать защищенную сессию и перенаправить на главную страницу
4. КОГДА пользователь вводит некорректные учетные данные, ТО Система ДОЛЖНА отобразить сообщение об ошибке без указания, что именно неверно (email или пароль)
5. КОГДА пользователь нажимает "Выйти", ТО Система ДОЛЖНА завершить сессию и перенаправить на страницу входа
6. Система ДОЛЖНА хранить пароли в зашифрованном виде с использованием bcrypt или аналогичного алгоритма
7. КОГДА пользователь запрашивает восстановление пароля, ТО Система ДОЛЖНА отправить ссылку для сброса пароля на email
8. Система ДОЛЖНА использовать JWT токены или session cookies для управления сессиями

### Требование 2: Профиль пользователя

**User Story:** Как пользователь, я хочу управлять своим профилем, чтобы хранить персональную информацию и настройки.

#### Критерии приемки

1. Система ДОЛЖНА хранить для каждого пользователя: email, имя, фамилию, дату регистрации, аватар
2. КОГДА пользователь открывает страницу профиля, ТО Система ДОЛЖНА отобразить текущие данные профиля
3. КОГДА пользователь изменяет данные профиля и сохраняет, ТО Система ДОЛЖНА обновить данные в База_Данных
4. КОГДА пользователь загружает новый аватар, ТО Система ДОЛЖНА сохранить изображение и обновить ссылку в профиле
5. Система ДОЛЖНА валидировать формат email при изменении
6. КОГДА пользователь меняет email, ТО Система ДОЛЖНА отправить письмо для подтверждения на новый адрес

### Требование 3: API для работы с тренировками

**User Story:** Как пользователь, я хочу создавать, редактировать и удалять тренировки, чтобы вести учет своих занятий.

#### Критерии приемки

1. КОГДА пользователь создает новую тренировку, ТО Бэкенд ДОЛЖЕН сохранить тренировку в База_Данных с привязкой к пользователю
2. КОГДА пользователь запрашивает список тренировок, ТО Бэкенд ДОЛЖЕН вернуть только тренировки текущего пользователя
3. КОГДА пользователь редактирует тренировку, ТО Бэкенд ДОЛЖЕН обновить данные только если тренировка принадлежит этому пользователю
4. КОГДА пользователь удаляет тренировку, ТО Бэкенд ДОЛЖЕН удалить запись только если тренировка принадлежит этому пользователю
5. Бэкенд ДОЛЖЕН валидировать структуру данных тренировки перед сохранением
6. КОГДА запрос содержит некорректные данные, ТО Бэкенд ДОЛЖЕН вернуть ошибку 400 с описанием проблемы
7. КОГДА пользователь пытается получить доступ к чужой тренировке, ТО Бэкенд ДОЛЖЕН вернуть ошибку 403
8. Бэкенд ДОЛЖЕН поддерживать пагинацию при запросе списка тренировок

### Требование 4: Структура базы данных

**User Story:** Как разработчик, я хочу иметь нормализованную структуру базы данных, чтобы эффективно хранить и запрашивать данные.

#### Критерии приемки

1. База_Данных ДОЛЖНА содержать таблицу users с полями: id, email, password_hash, first_name, last_name, avatar_url, created_at, updated_at
2. База_Данных ДОЛЖНА содержать таблицу workouts с полями: id, user_id, date, comment, created_at, updated_at
3. База_Данных ДОЛЖНА содержать таблицу skill_blocks с полями: id, workout_id, exercise_name, sets_count, reps_array, weights_array, max_weight
4. База_Данных ДОЛЖНА содержать таблицу wod_blocks с полями: id, workout_id, wod_type, level, time_cap, is_ladder, ladder_rounds, result_type, result_value
5. База_Данных ДОЛЖНА содержать таблицу wod_exercises с полями: id, wod_block_id, exercise_name, reps, ladder_reps_array, weight
6. База_Данных ДОЛЖНА использовать внешние ключи для связи таблиц с каскадным удалением
7. База_Данных ДОЛЖНА иметь индексы на поля user_id и date для оптимизации запросов
8. База_Данных ДОЛЖНА использовать PostgreSQL в качестве СУБД

### Требование 5: Фильтрация и поиск тренировок

**User Story:** Как пользователь, я хочу фильтровать тренировки по дате и упражнениям, чтобы быстро находить нужные записи.

#### Критерии приемки

1. КОГДА пользователь выбирает период дат, ТО Бэкенд ДОЛЖЕН вернуть только тренировки в указанном диапазоне
2. КОГДА пользователь выбирает упражнение, ТО Бэкенд ДОЛЖЕН вернуть только тренировки, содержащие это упражнение
3. КОГДА пользователь выбирает тип блока (Skill/WOD), ТО Бэкенд ДОЛЖЕН вернуть только тренировки с блоками выбранного типа
4. Бэкенд ДОЛЖЕН поддерживать комбинацию фильтров (дата + упражнение + тип)
5. КОГДА фильтры не заданы, ТО Бэкенд ДОЛЖЕН вернуть все тренировки пользователя
6. Бэкенд ДОЛЖЕН возвращать результаты отсортированными по дате (от новых к старым)

### Требование 6: Расчет статистики

**User Story:** Как пользователь, я хочу видеть статистику по своим тренировкам, чтобы отслеживать прогресс.

#### Критерии приемки

1. КОГДА пользователь открывает страницу статистики, ТО Бэкенд ДОЛЖЕН рассчитать количество тренировок за выбранный период
2. КОГДА пользователь выбирает период, ТО Бэкенд ДОЛЖЕН рассчитать количество Skill и WOD сессий отдельно
3. Бэкенд ДОЛЖЕН определять личные рекорды (PR) как максимальные веса по каждому упражнению
4. КОГДА пользователь сохраняет тренировку с новым максимальным весом, ТО Бэкенд ДОЛЖЕН обновить соответствующий PR
5. Бэкенд ДОЛЖЕН рассчитывать количество новых PR за выбранный период
6. КОГДА пользователь запрашивает статистику, ТО Бэкенд ДОЛЖЕН вернуть данные в течение 2 секунд
7. Бэкенд ДОЛЖЕН поддерживать фильтрацию статистики по периодам: неделя, месяц, год, все время

### Требование 7: Данные для графиков прогресса

**User Story:** Как пользователь, я хочу видеть графики прогресса по упражнениям, чтобы визуально оценивать свое развитие.

#### Критерии приемки

1. КОГДА пользователь выбирает упражнение, ТО Бэкенд ДОЛЖЕН вернуть историю максимальных весов по датам
2. Бэкенд ДОЛЖЕН поддерживать группировку данных по дням, неделям и месяцам
3. КОГДА выбрана группировка по неделям, ТО Бэкенд ДОЛЖЕН вернуть максимальный вес за каждую неделю
4. КОГДА выбрана группировка по месяцам, ТО Бэкенд ДОЛЖЕН вернуть максимальный вес за каждый месяц
5. Бэкенд ДОЛЖЕН возвращать данные в формате, готовом для отображения в Chart.js
6. КОГДА данных для графика нет, ТО Бэкенд ДОЛЖЕН вернуть пустой массив

### Требование 8: Миграция данных из localStorage

**User Story:** Как пользователь с существующими данными в localStorage, я хочу перенести их в новую систему, чтобы не потерять историю тренировок.

#### Критерии приемки

1. КОГДА пользователь впервые входит в систему, ТО Система ДОЛЖНА проверить наличие данных в localStorage
2. КОГДА данные в localStorage обнаружены, ТО Система ДОЛЖНА предложить импортировать их
3. КОГДА пользователь подтверждает импорт, ТО Система ДОЛЖНА отправить данные на Бэкенд для сохранения
4. Бэкенд ДОЛЖЕН валидировать импортируемые данные перед сохранением
5. КОГДА импорт завершен успешно, ТО Система ДОЛЖНА очистить localStorage и отобразить уведомление
6. КОГДА импорт завершен с ошибками, ТО Система ДОЛЖНА отобразить список ошибок и сохранить корректные записи
7. Система ДОЛЖНА предотвращать дублирование данных при повторном импорте

### Требование 9: Обработка ошибок и валидация

**User Story:** Как пользователь, я хочу получать понятные сообщения об ошибках, чтобы понимать, что пошло не так.

#### Критерии приемки

1. КОГДА происходит ошибка на сервере, ТО Бэкенд ДОЛЖЕН вернуть HTTP статус код соответствующий типу ошибки
2. КОГДА происходит ошибка валидации, ТО Бэкенд ДОЛЖЕН вернуть 400 с описанием всех невалидных полей
3. КОГДА пользователь не авторизован, ТО Бэкенд ДОЛЖЕН вернуть 401
4. КОГДА пользователь пытается получить доступ к чужим данным, ТО Бэкенд ДОЛЖЕН вернуть 403
5. КОГДА запрашиваемый ресурс не найден, ТО Бэкенд ДОЛЖЕН вернуть 404
6. КОГДА происходит внутренняя ошибка сервера, ТО Бэкенд ДОЛЖЕН вернуть 500 и залогировать детали ошибки
7. Система ДОЛЖНА отображать пользователю понятные сообщения об ошибках на русском языке
8. КОГДА соединение с База_Данных потеряно, ТО Система ДОЛЖНА отобразить сообщение о временной недоступности

### Требование 10: Производительность и оптимизация

**User Story:** Как пользователь, я хочу, чтобы приложение работало быстро, чтобы комфортно им пользоваться.

#### Критерии приемки

1. КОГДА пользователь загружает главную страницу, ТО Система ДОЛЖНА отобразить контент в течение 2 секунд
2. КОГДА пользователь запрашивает список тренировок, ТО Бэкенд ДОЛЖЕН вернуть ответ в течение 1 секунды
3. КОГДА пользователь сохраняет тренировку, ТО Бэкенд ДОЛЖЕН обработать запрос в течение 500 миллисекунд
4. Бэкенд ДОЛЖЕН использовать индексы базы данных для оптимизации запросов
5. Система ДОЛЖНА использовать кэширование для статических ресурсов
6. КОГДА пользователь загружает изображение аватара, ТО Система ДОЛЖНА оптимизировать его размер до 500KB

### Требование 11: Безопасность

**User Story:** Как пользователь, я хочу, чтобы мои данные были защищены, чтобы никто посторонний не мог получить к ним доступ.

#### Критерии приемки

1. Система ДОЛЖНА использовать HTTPS для всех соединений
2. Бэкенд ДОЛЖЕН валидировать и санитизировать все входящие данные для предотвращения SQL-инъекций
3. Бэкенд ДОЛЖЕН использовать параметризованные запросы для всех операций с База_Данных
4. Система ДОЛЖНА защищать от CSRF атак с использованием токенов
5. Бэкенд ДОЛЖЕН ограничивать количество запросов от одного IP (rate limiting)
6. КОГДА пользователь вводит пароль, ТО Система ДОЛЖНА требовать минимум 8 символов, включая буквы и цифры
7. Система ДОЛЖНА использовать HTTP-only cookies для хранения токенов сессии
8. Бэкенд ДОЛЖЕН логировать все попытки несанкционированного доступа

### Требование 12: Развертывание на Vercel

**User Story:** Как владелец продукта, я хочу развернуть приложение на Vercel, чтобы оно было доступно пользователям в интернете.

#### Критерии приемки

1. Система ДОЛЖНА быть развернута на платформе Vercel
2. КОГДА происходит push в main ветку, ТО Vercel ДОЛЖЕН автоматически запустить деплой
3. База_Данных ДОЛЖНА быть развернута на Vercel Postgres или Supabase
4. Система ДОЛЖНА использовать переменные окружения для хранения секретов (database URL, JWT secret)
5. КОГДА деплой завершен, ТО Система ДОЛЖНА быть доступна по HTTPS URL
6. Система ДОЛЖНА иметь настроенный custom домен
7. КОГДА происходит ошибка при деплое, ТО Vercel ДОЛЖЕН отправить уведомление
8. Система ДОЛЖНА использовать production и preview окружения

### Требование 13: Мониторинг и логирование

**User Story:** Как разработчик, я хочу видеть логи и метрики приложения, чтобы быстро находить и исправлять проблемы.

#### Критерии приемки

1. Бэкенд ДОЛЖЕН логировать все HTTP запросы с временем выполнения
2. КОГДА происходит ошибка, ТО Бэкенд ДОЛЖЕН логировать stack trace и контекст запроса
3. Система ДОЛЖНА использовать структурированное логирование (JSON формат)
4. Система ДОЛЖНА интегрироваться с Vercel Analytics для отслеживания производительности
5. Бэкенд ДОЛЖЕН логировать медленные запросы к База_Данных (более 1 секунды)
6. Система ДОЛЖНА хранить логи минимум 7 дней

### Требование 14: Резервное копирование данных

**User Story:** Как владелец продукта, я хочу иметь резервные копии данных, чтобы восстановить систему в случае сбоя.

#### Критерии приемки

1. База_Данных ДОЛЖНА создавать автоматические резервные копии ежедневно
2. Система ДОЛЖНА хранить резервные копии минимум 7 дней
3. КОГДА создается резервная копия, ТО Система ДОЛЖНА проверять ее целостность
4. Система ДОЛЖНА предоставлять возможность восстановления из резервной копии
5. КОГДА происходит критическая ошибка База_Данных, ТО Система ДОЛЖНА отправить уведомление администратору

### Требование 15: Адаптация существующего UI

**User Story:** Как пользователь, я хочу, чтобы существующий интерфейс работал с новым бэкендом, чтобы не переучиваться.

#### Критерии приемки

1. КОГДА пользователь создает тренировку через существующий UI, ТО данные ДОЛЖНЫ сохраняться через API
2. КОГДА пользователь открывает историю тренировок, ТО данные ДОЛЖНЫ загружаться из База_Данных через API
3. КОГДА пользователь открывает статистику, ТО данные ДОЛЖНЫ рассчитываться на Бэкенд и отображаться в существующих графиках
4. Система ДОЛЖНА сохранить все существующие функции UI (фильтры, пагинация, графики)
5. КОГДА происходит ошибка API, ТО UI ДОЛЖЕН отображать понятное сообщение пользователю
6. Система ДОЛЖНА показывать индикаторы загрузки при выполнении запросов к API

### Требование 16: Страницы регистрации и входа

**User Story:** Как новый пользователь, я хочу иметь удобные страницы регистрации и входа, чтобы быстро начать пользоваться приложением.

#### Критерии приемки

1. Система ДОЛЖНА иметь страницу регистрации с полями: email, пароль, подтверждение пароля, имя, фамилия
2. Система ДОЛЖНА иметь страницу входа с полями: email, пароль
3. КОГДА пользователь вводит невалидный email, ТО Система ДОЛЖНА отобразить ошибку валидации
4. КОГДА пароли не совпадают при регистрации, ТО Система ДОЛЖНА отобразить ошибку
5. Страницы ДОЛЖНЫ быть адаптивными и соответствовать дизайну существующего приложения
6. Система ДОЛЖНА иметь ссылку "Забыли пароль?" на странице входа
7. КОГДА регистрация успешна, ТО Система ДОЛЖНА автоматически войти в систему и перенаправить на главную страницу
