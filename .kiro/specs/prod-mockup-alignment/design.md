# Bugfix Design: Приведение продакшн версии в соответствие с эталонными макетами

## Обзор

Продакшн версия приложения CrossFit Tracker имеет значительные расхождения с эталонными макетами в `public/workout-tracker/`. Необходимо привести Next.js реализацию в полное соответствие с эталонными макетами по визуальному представлению и функциональности компонентов.

Основные проблемы:
- Главная страница отображает только одну карточку статистики вместо трех
- Страница истории использует стандартный HTML5 date picker вместо кастомного календаря
- Отсутствует страница общей статистики `/dashboard/stats`
- Страница создания тренировки не имеет всех полей и функций из эталона
- Страница детального просмотра не имеет кнопки редактирования и расчета 1RM

## Глоссарий

- **Bug_Condition (C)**: Условие, при котором продакшн версия отображает интерфейс, не соответствующий эталонным макетам
- **Property (P)**: Желаемое поведение - полное соответствие эталонным макетам по визуальному представлению и функциональности
- **Preservation**: Существующая функциональность (аутентификация, работа с БД, API) должна остаться неизменной
- **Эталонные макеты**: Файлы в `public/workout-tracker/` (index.html, mvp-styles.css, mvp-script-v3.js)
- **Продакшн версия**: Next.js приложение в `app/dashboard/`

## Детали бага

### Условие возникновения бага (Fault Condition)

Баг проявляется когда пользователь взаимодействует с любой страницей приложения и видит интерфейс, отличающийся от эталонных макетов.

**Формальная спецификация:**
```
FUNCTION isBugCondition(input)
  INPUT: input типа { page: string, userAction: string }
  OUTPUT: boolean
  
  RETURN (input.page IN ['dashboard', 'workouts', 'workouts/new', 'workouts/[id]', 'stats'])
         AND (визуальноеПредставление(input.page) != эталонноеПредставление(input.page)
              OR функциональность(input.page) != эталоннаяФункциональность(input.page))
END FUNCTION
```

### Примеры проявления бага


**Главная страница:**
- Текущее: Отображается только карточка "Тоннаж в этом месяце"
- Ожидаемое: Три карточки - "Тренировок в этом месяце", "Лучший вес" (с названием упражнения и датой), "Тренировочных дней подряд" (с иконкой 🔥)

**Страница истории:**
- Текущее: Стандартный HTML5 `<input type="date">`
- Ожидаемое: Кастомный date picker с визуальным календарем на 3 месяца, пресетами периодов, индикаторами тренировок

**Страница статистики:**
- Текущее: Перенаправление на `/dashboard/exercise` вместо общей статистики
- Ожидаемое: Страница `/dashboard/stats` с селектором периода, сеткой статистики, личными рекордами и графиком прогресса

**Страница создания тренировки:**
- Текущее: Упрощенная форма без селектора количества подходов, поля максимального веса, подсказок о прошлых результатах
- Ожидаемое: Полная форма с селектором подходов (1-12), полем максимального веса, подсказками "В прошлый раз: X кг", режимом "Лесенка" для WOD

## Ожидаемое поведение

### Требования к сохранению функциональности (Preservation Requirements)

**Неизменное поведение:**
- Аутентификация пользователей должна продолжать работать корректно
- Все операции с базой данных (создание, чтение, обновление, удаление тренировок) должны работать без изменений
- API endpoints должны возвращать корректные ответы
- Валидация данных должна продолжать работать
- Адаптивный дизайн для мобильных устройств должен сохраниться
- Темная цветовая схема должна применяться

**Область изменений:**
Все изменения касаются только визуального представления и UI компонентов. Логика работы с данными, API и бизнес-логика остаются неизменными.

## Гипотеза о первопричине

На основе анализа кода выявлены следующие причины расхождений:

1. **Неполная реализация компонентов**: Next.js версия была создана как упрощенная версия, не включающая все элементы из эталонных макетов
   - Главная страница: Не реализованы карточки "Лучший вес" и "Тренировочных дней подряд"
   - История: Использован стандартный HTML5 date picker вместо кастомного компонента

2. **Отсутствующие страницы**: Страница общей статистики `/dashboard/stats` не была создана
   - Навигация ведет на `/dashboard/exercise` вместо `/dashboard/stats`

3. **Упрощенные формы**: Форма создания тренировки не включает все поля из эталона
   - Отсутствует селектор количества подходов для Skill блоков
   - Нет поля "Максимальный вес"
   - Не реализованы подсказки о прошлых результатах
   - Отсутствует режим "Лесенка" с динамическими полями для раундов

4. **Неполная страница деталей**: Страница просмотра тренировки не имеет кнопки редактирования и расчета 1RM

## Свойства корректности (Correctness Properties)

Property 1: Fault Condition - Соответствие визуального представления эталонным макетам

_Для любой_ страницы приложения, где визуальное представление или функциональность отличается от эталонных макетов, 
исправленная версия ДОЛЖНА отображать интерфейс в полном соответствии с эталонными макетами, включая все элементы UI, 
стили, расположение компонентов и интерактивные элементы.

**Validates: Requirements 2.1, 2.2, 2.3, 2.4, 2.5, 2.6, 2.7, 2.8, 2.9, 2.10, 2.11, 2.12, 2.13, 2.14, 2.15, 2.16, 2.17, 2.18, 2.19, 2.20, 2.21, 2.22, 2.23, 2.24, 2.25, 2.26**

Property 2: Preservation - Сохранение существующей функциональности

_Для любого_ взаимодействия с приложением, которое НЕ касается визуального представления (аутентификация, работа с БД, 
API запросы, валидация), исправленный код ДОЛЖЕН производить точно такой же результат, как и оригинальный код, 
сохраняя всю существующую бизнес-логику и функциональность работы с данными.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 3.8, 3.9, 3.10**

## Стратегия тестирования

### Подход к валидации

Стратегия тестирования следует двухфазному подходу: сначала выявить несоответствия между текущей реализацией и эталонными макетами 
на НЕИСПРАВЛЕННОМ коде, затем проверить, что исправления работают корректно и сохраняют существующую функциональность.

### Exploratory Fault Condition Checking

**Цель**: Выявить конкретные несоответствия между текущей реализацией и эталонными макетами ДО внесения исправлений. 
Подтвердить или опровергнуть анализ первопричины. Если опровергнем, потребуется пересмотр гипотезы.

**План тестирования**: Создать визуальные тесты и тесты компонентов, которые сравнивают текущую реализацию с эталонными макетами. 
Запустить эти тесты на НЕИСПРАВЛЕННОМ коде для наблюдения за несоответствиями и понимания первопричины.

**Тестовые случаи:**
1. **Тест главной страницы**: Проверить количество карточек статистики (ожидается сбой - только 1 вместо 3)
2. **Тест date picker**: Проверить наличие кастомного календаря (ожидается сбой - используется HTML5 input)
3. **Тест страницы статистики**: Проверить существование `/dashboard/stats` (ожидается сбой - страница не существует)
4. **Тест формы Skill**: Проверить наличие селектора подходов и поля максимального веса (ожидается сбой - поля отсутствуют)
5. **Тест режима лесенки**: Проверить наличие checkbox "Лесенка" и динамических полей (ожидается сбой - функция не реализована)
6. **Тест кнопки редактирования**: Проверить наличие кнопки "✏️ Редактировать" на странице деталей (ожидается сбой - кнопка отсутствует)

**Ожидаемые контрпримеры:**
- Главная страница отображает только карточку "Тоннаж" вместо трех карточек
- Страница истории использует стандартный HTML5 date picker
- Навигация "Статистика" ведет на `/dashboard/exercise` вместо `/dashboard/stats`
- Форма создания тренировки не имеет всех полей из эталона
- Возможные причины: неполная реализация компонентов, отсутствующие страницы, упрощенные формы

### Fix Checking

**Цель**: Проверить, что для всех входных данных, где выполняется условие бага, исправленная функция производит ожидаемое поведение.

**Псевдокод:**
```
FOR ALL input WHERE isBugCondition(input) DO
  result := renderPage_fixed(input.page)
  ASSERT соответствуетЭталону(result, input.page)
END FOR
```

**План тестирования:**
1. **Визуальные регрессионные тесты**: Сравнить скриншоты исправленных страниц с эталонными макетами
2. **Компонентные тесты**: Проверить наличие всех элементов UI из эталонных макетов
3. **Функциональные тесты**: Проверить работу всех интерактивных элементов (date picker, фильтры, формы)

### Preservation Checking

**Цель**: Проверить, что для всех входных данных, где условие бага НЕ выполняется (функциональность, не связанная с UI), 
исправленная функция производит тот же результат, что и оригинальная функция.

**Псевдокод:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT apiCall_original(input) = apiCall_fixed(input)
  ASSERT dataProcessing_original(input) = dataProcessing_fixed(input)
END FOR
```

**Подход к тестированию**: Property-based testing рекомендуется для проверки сохранения функциональности, потому что:
- Автоматически генерирует множество тестовых случаев для различных входных данных
- Выявляет граничные случаи, которые могут быть пропущены в ручных unit тестах
- Предоставляет сильные гарантии, что поведение не изменилось для всех операций с данными

**План тестирования**: Наблюдать поведение на НЕИСПРАВЛЕННОМ коде для операций с данными, затем написать property-based тесты, 
фиксирующие это поведение.

**Тестовые случаи:**
1. **Сохранение аутентификации**: Проверить, что вход и выход из системы работают идентично
2. **Сохранение операций с БД**: Проверить, что создание, чтение, обновление и удаление тренировок работают без изменений
3. **Сохранение API ответов**: Проверить, что все API endpoints возвращают те же данные
4. **Сохранение валидации**: Проверить, что валидация форм работает идентично

### Unit Tests

- Тест компонента CustomDatePicker: проверка отображения календаря, навигации, выбора дат
- Тест компонента ExerciseFilter: проверка фильтрации по упражнениям
- Тест формы Skill блока: проверка динамического создания полей подходов
- Тест режима лесенки WOD: проверка динамического создания полей раундов
- Тест расчета 1RM: проверка корректности формулы Brzycki
- Тест маски ввода MM:SS: проверка форматирования времени
- Тест автоматического скрытия поля веса для кардио упражнений

### Property-Based Tests

- Генерация случайных дат и проверка корректной работы date picker
- Генерация случайных конфигураций тренировок и проверка сохранения в БД
- Генерация случайных фильтров и проверка корректной фильтрации данных
- Тестирование сохранения поведения API для различных входных параметров

### Integration Tests

- Полный flow создания тренировки с использованием всех новых полей
- Полный flow фильтрации истории с использованием кастомного date picker
- Полный flow просмотра статистики с переключением периодов
- Полный flow редактирования тренировки через кнопку на странице деталей
- Проверка адаптивности на различных размерах экрана (мобильный, планшет, десктоп)

### Visual Regression Tests

- Скриншотное тестирование всех страниц в сравнении с эталонными макетами
- Проверка соответствия цветов, отступов, шрифтов, размеров элементов
- Проверка адаптивного дизайна на различных разрешениях
